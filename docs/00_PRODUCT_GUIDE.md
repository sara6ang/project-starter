## 1. 무슨 문제를 푸는가

> **"직원이 바뀔 때마다 A부터 다시 가르쳐야 한다."**

F&B 매장은 아르바이트 비중이 높고 근속이 짧습니다. "가르치는 일"이 예외가 아니라 매일 반복되는 일입니다.

레시피, 청소 순서, 마감 절차 — 대부분 사장 머릿속에만 있거나 카톡·손글씨 노트로 흩어져 있습니다. 매뉴얼이 없는 게 아니라, **매뉴얼이 직원에게 전달되고 지켜지는지 확인할 방법이 없는 것**이 진짜 문제입니다.

**Tongss는 매장 운영 시스템(POS, 재고관리 시스템) 자체를 새로 만드는 프로젝트가 아닙니다.** 토스플레이스가 이미 결제·재고 기능을 갖고 있습니다. Tongss가 채우는 자리는 그 위에 있는 **운영 지식(Knowledge)과 업무 수행(Process)을 잇는 연결 레이어**입니다:

1. 운영 방법을 정리하고
2. 직원에게 전달하고
3. 직원이 실제로 수행했는지 확인하고
4. 사장이 그 결과를 확인할 수 있게 한다

---

## 2. 우리가 만드는 것 — 세 기둥

| 기둥 | 해결하는 것 |
|---|---|
| **운영 지식 (매뉴얼)** | 흩어진 지식을 한 곳에. 직원이 필요한 순간에 꺼내 본다 |
| **업무 수행 확인 (체크리스트 · 재고 확인)** | 정해진 업무를 직원이 실제로 했는지 기록하고, 사장이 확인한다 |
| **직원 파악** | 누가 무엇을 익혔고 무엇을 수행했는지 사장이 한눈에 안다 |

세 가지는 결국 하나의 질문에 대한 답입니다: **"운영 지식이 전달되고, 업무가 실제로 수행되는가?"** (사장 입장에서는 "내가 없어도 매장이 같은 품질로 돌아가는가?"와 같은 말입니다.)

## 3. Demo Day에 보여줄 한 줄 ⭐ (가장 중요)

> **사장(이대표)이 매뉴얼을 등록한다 → 직원(김스태프)이 학습하고 오픈·마감·재고 확인 같은 업무를 수행한다 → 점주가 그 수행 여부를 확인한다 → 토스플레이스(박세일즈)가 org에서 그 매장의 상태를 확인한다.**

이 문장이 이 프로젝트의 **정본(定本)**입니다. 다른 문서에서 "Demo Day 시나리오"라고 하면 항상 이 문장을 가리킵니다.

**이 한 줄에 들어있지 않은 기능은 지금 우선순위가 아닙니다.** 뭘 먼저 만들지 헷갈리면 이 문장에 다시 물어보세요 — "이게 이 줄을 완성하는 데 필요한가?"

## 4. 페르소나별 핵심 기능

자세한 페르소나 설명은 `01_PERSONAS.md` 참조. 여기는 "그래서 뭘 만드는지"만 요약합니다.

### 이대표 (사장) — TongssApp
| 페인포인트 | 기능 |
|---|---|
| 신입 교육이 매번 처음부터 | 매뉴얼 등록 (5분 이내, 사진+짧은 텍스트) |
| 체크리스트가 안 지켜짐 | 오픈/마감 체크리스트 + 완료 여부가 사장에게 보임 |
| 누가 뭘 했는지 모름 | 직원별 학습·업무 수행 상태 대시보드 (체크리스트 + 재고 확인 포함) |

### 김스태프 (직원) — TongssApp
| 페인포인트 | 기능 |
|---|---|
| 뭘 해야 하는지 모름 | 매뉴얼 뷰어 (역할/상황별 진입) |
| 매뉴얼이 너무 길다 | 한 화면 = 한 동작, 이미지 중심 (설계 원칙) |
| — | 재고 확인 체크리스트 (부족한 품목 표시, 한 손 입력) — *수량 계산이 아니라 "확인했는지" 기록* |

### 박세일즈 (토스 실무자) — TongssOrg
| 페인포인트 | 기능 |
|---|---|
| 매장 운영 상태가 안 보임 | 매장(Account) 레코드에 활성 상태 필드 |
| 도입 현황 파악이 수작업 | 리스트뷰로 필터 가능한 도입/활성 상태 |
| 매장별 맥락 없음 | 매장별 히스토리 (등록 매뉴얼 수, 학습·업무 수행 완료율) |

### 박오너 (토스 의사결정자)
별도 기능 없음 — 박세일즈 화면에서 자동으로 집계되는 숫자(도입률, 활성도)로 판단합니다.

## 5. 이번에 만드는 것 / 안 만드는 것

### ✅ 만든다 (5.5주 안에)

**TongssApp**
- [ ] **Entry Code 진입** (`S01O`=1번 매장 사장, `S01E01`=1번 매장 1번 직원 — 실제 로그인 시스템 아님, 코드로 매장·역할만 구분)
- [ ] 매뉴얼 등록 (사진 + 짧은 텍스트)
- [ ] 매뉴얼 뷰어 (직원용)
- [ ] 오픈/마감 체크리스트 + 완료 기록
- [ ] **재고 확인 체크리스트** (부족 품목 표시 + 완료 기록 — *수량 계산이 아니라 "오늘 확인했는가"를 기록*)
- [ ] 직원별 학습·업무 수행 완료 상태 대시보드

**TongssOrg**
- [ ] 매장(Account) + 도입/활성 상태 필드
- [ ] 매장별 히스토리 (등록 매뉴얼 수, 학습·업무 수행 완료율)
- [ ] 리스트뷰 필터 (활성/방치 매장)

**연동**
- [ ] TongssApp → TongssOrg 데이터 파이프라인 (`04_DATA_CONTRACT.md` 기준)

### ❌ 안 만든다

- **실제 로그인/회원가입/비밀번호 시스템** — Entry Code(`S01O` 등)로 대체. 인증은 MVP에서 의도적으로 미룬다
- 결제/POS 기능 — 토스플레이스 영역
- **재고 수량 관리 자체** — 토스플레이스가 이미 제공하는 기능. Tongss는 "직원이 확인했는가"만 다룬다
- 고객관리(CRM/멤버십) — 도도포인트·캐시노트와 중복
- 발주 자동화, 원가·마진 계산 — 다음 단계 아이디어 (`archive/04_INITIAL_IDEAS.md`)
- 다점포 통합 대시보드 — 1차 타깃은 개인 매장·소규모 브랜드
- 박오너용 별도 지표 대시보드 — 박세일즈 화면에서 자동 집계로 대체

### 🤔 아직 정하지 않음 (Week 1에 팀이 결정)

- 매뉴얼에 카테고리/태그를 둘 것인가, 완전 무순서 리스트로 시작할 것인가
- 체크리스트 항목을 사장이 직접 만드는가, 기본 템플릿을 제공하는가

> 결정되면 이 목록에서 지우고 `07_DECISIONS.md`에 기록합니다.

## 6. Demo Day 성공 확인 체크리스트

| 확인 항목 | 통과 조건 |
|---|---|
| 사장이 매뉴얼을 등록한다 | TongssApp에서 실제 매뉴얼 1건 이상 등록 완료 |
| 직원이 학습하고 업무를 수행한다 | 매뉴얼 "다 봤어요" 체크 + 오픈/마감/재고 확인 체크리스트 완료 |
| 점주가 수행 여부를 확인한다 | 사장 대시보드에서 학습·업무 수행 상태 확인 가능 |
| 박세일즈가 org에서 확인한다 | TongssOrg 매장 레코드에 등록 매뉴얼 수·업무 수행 완료율이 실제 데이터로 표시 |
| 전체 흐름이 실 데이터로 연결 | 더미 데이터가 아니라 TongssApp에서 만든 데이터가 org까지 도달 |

이 다섯 가지가 Week 4 종료 조건이자 Demo Day 리허설 체크리스트입니다.

## 7. 스코프를 줄여야 할 때 (우선순위 원칙)

Week 3 중간 점검에서 뭔가 잘라야 한다면, 아래 순서로 자릅니다.

1. Nice-to-have로 표시된 것부터
2. In 스코프 중 "구현은 됐지만 데모 흐름에 필수는 아닌" 디테일 (예: 매뉴얼 카테고리, 세부 통계)
3. UX 완성도 (다듬는 것보다 흐름이 끊기지 않는 게 우선)

**자르지 않는 것:** §3의 한 줄 시나리오를 구성하는 최소 기능 (매뉴얼 등록 → 학습 → 업무 수행 → 점주 확인 → org 반영)

**새 기능을 추가하는 게 아니라, 이미 있는 업무(오픈/마감/재고 확인 등)를 더 쉽게 교육하고, 더 쉽게 수행하고, 더 쉽게 확인하게 만드는 것**이 Tongss의 역할입니다. 스코프 판단이 애매할 때는 이 기준으로 돌아오세요.

## 8. 왜 토스플레이스가 이걸 원할까 (3줄 요약)

토스플레이스는 이미 37만 매장의 결제망을 갖고 있지만, 계열사 중 매출이 가장 작고 자본잠식 상태입니다. Square·Toast는 "결제 데이터 위에 운영 데이터를 쌓고, 구독형 소프트웨어로 수익화"하는 단계에서 성장했습니다. 토스플레이스는 아직 이 단계를 밟지 않았고, Tongss(운영 지식 + 업무 수행 데이터)가 그 자리를 채웁니다.

전체 재무 분석·벤치마크 데이터는 `archive/01_WHY_RESEARCH.md` 참조.

## 9. Future Vision (MVP 범위 밖 — 방향성 참고용)

⚠️ 아래는 이번 5.5주 스코프가 아닙니다. §5의 In/Out 표와 혼동하지 마세요 — "우리가 앞으로 어디로 갈 수 있는가"를 보여주는 아이디어입니다.

### Face Check-in (출퇴근 인증)

토스는 이미 Face 인증(페이스페이) 기능을 갖고 있습니다. 장기적으로 Tongss도 이 흐름을 그릴 수 있습니다:

**Face 인증 → 출근 기록 생성 → 오늘 체크리스트 자동 표시 → 업무 시작**

**이번엔 이 정도만 (UI 목업, 실제 인증 없음)**
- [ ] 출퇴근 기록 화면
- [ ] 오늘 출근 여부
- [ ] 출근 시간 / 퇴근 시간
- [ ] 근무 상태

**만들지 않는 것:** Face Recognition 기술 자체. "향후 토스 플랫폼 기능과 연계 가능한 아이디어"로만 화면에 표시합니다.

### 화면 예시 (목업, 실제 인증 없음)

```

──────────────
😊 Face Verified
07:58
출근 완료
──────────────
오늘 해야 할 일
☑ 오픈 체크리스트
☐ 재고 확인
☐ 패티 해동
☐ 냉장고 온도 확인
──────────────
퇴근 예정
21:00
```

### Demo Day 발표 포인트

> "현재는 UI만 준비했습니다. 실제 토스의 Face 인증 기능과 연동된다면, 직원 인증과 업무 시작을 하나의 경험으로 연결할 수 있습니다."

기술을 과장하지 않으면서 확장 가능성을 보여주는 데모 포인트로 씁니다.
