## 페르소나 1 — 이대표 (F&B 매장 사장)

**한 줄:** 가르치는 데 지친 사장. 매장이 나 없이도 돌아가길 원한다.

### 프로필
- 카페 운영, 직원 8명 (정직원 + 아르바이트)
- 알바 교체가 잦다 — "가르치는 일"이 예외가 아니라 상시 업무

### 페인포인트
1. **같은 말을 하루에도 수십 번 반복한다.** 신입이 올 때마다 A부터.
2. **신입 교육이 스트레스다.** 매번 처음부터, 매번 혼자.
3. **체크리스트가 안 지켜진다.** 만들어놔도 현장에서 무시된다.
4. **매뉴얼을 안 읽는다.** 있어도 안 본다 — 배포와 학습은 다른 문제.
5. **누가 뭘 했는지 모른다.** "이거 알죠?"라고 물어야만 알 수 있다.

### 원하는 것 (핵심 동기)
> **매장이 나 없이도 돌아가길 원한다.**
나머지 모든 요구사항은 이 한 문장에서 파생된다.

### 학습 관점 `[리뷰 세션에서 은영·혜준 인풋 필수]`
- 이대표는 "가르치는 사람"이지 콘텐츠 제작자가 아니다. **매뉴얼 등록이 글쓰기처럼 느껴지면 안 된다.**
- 이미 머릿속/카톡에 있는 것을 옮기는 경험이어야 한다. 백지에서 시작하게 하면 실패한다.
- "체크리스트가 안 지켜진다"는 콘텐츠 문제가 아니라 **확인·강제 장치의 부재**일 수 있다 — PRD에서 "체크리스트 완료 여부가 사장에게 보이는가"를 별도 기능으로 다룰 것.

### 성공의 정의
새 직원이 들어왔을 때, 이대표가 "이거 보고 시작해요"라고 말하고 자기 일을 하러 갈 수 있다.

### 제품에 주는 요구사항
- 매뉴얼 등록이 **5분 안에** 끝나야 한다 (사진/짧은 텍스트 중심, 서식 최소)
- 직원별 학습·체크리스트 완료 상태가 **한 화면에** 보여야 한다
- 재고는 "숫자 입력"이 아니라 "부족한 것 알림"으로 도달해야 한다

## 페르소나 2 — 김스태프 (매장 직원 / 아르바이트)

**한 줄:** 그냥 시키는 대로 하면 된다고 생각하는, 근무 2개월차 신입.

### 프로필
- 아르바이트, 근무 2개월차

### 페인포인트
1. **뭘 해야 하는지 모른다.** 지시가 명확하지 않으면 그냥 멈춘다.
2. **물어보기 눈치 보인다.** 특히 바쁠 때, 특히 같은 걸 두 번째 물을 때.
3. **실수하면 혼난다.** 확신 없이 하고, 나중에 지적받는다.
4. **매뉴얼이 너무 길다.** ⭐ 있어도 안 읽는 이유 — 정보량 자체가 부담.

### 원하는 것 / 마인드셋
> **그냥 시키는 대로 하면 된다.**
김스태프는 능동적 학습자가 아니다. 이해나 맥락보다 **정확한 지시**를 원한다.

### 학습 관점 ⭐ `[제품의 핵심 — 은영·혜준 인풋 필수]`
- **일하는 중에 보는 문서다.** 공부하듯 읽는 게 아니라, 손에 트레이를 든 채로 3초 안에 답을 찾는다.
- **"매뉴얼이 너무 길다"는 페인포인트가 곧 설계 원칙이다.** 한 화면 = 한 동작. 스크롤 긴 문서는 실패다.
- **검색보다 맥락.** "지금 마감 시간" → 마감 체크리스트가 먼저 보여야 한다.
- "그냥 시키는 대로"라는 마인드셋을 존중할 것 — 왜(why)를 설명하려 들지 말고, 무엇을(what)·어떻게(how)만 명확히. 이해를 강요하면 오히려 이탈한다.
- 학습 완료 표시는 **감시가 아니라 성취감**으로 설계되어야 한다. `[리뷰 세션 논의 필요]`

### 성공의 정의
모르는 게 생겼을 때, 사람을 찾는 대신 폰을 꺼내서 3초 안에 답을 본다.

### 제품에 주는 요구사항
- 로그인·진입이 극도로 가벼워야 한다 (앱 설치 요구는 이탈 요인)
- 매뉴얼은 **짧은 단계 + 이미지** 단위, 절대 길게 쓰지 않는다
- 재고 입력은 현장에서 한 손으로 가능해야 한다
- "다 봤어요" 체크가 부담이 아니라 진행 표시로 느껴져야 한다

## 페르소나 3A — 박오너 (토스플레이스 PM / 의사결정자)

**한 줄:** POS만으로는 차별화가 끝났다고 판단한 의사결정자. Square처럼 운영 플랫폼이 되어야 한다고 믿는다.

### 프로필
- 토스플레이스 신사업/전략 담당, 의사결정 권한 보유

### 페인포인트
1. **POS만으로 차별화가 어렵다.** 경쟁사도 단말기는 다 있다.
2. Square처럼 운영 플랫폼이 되지 않으면 성장이 멈춘다는 위기감.

### 원하는 것 (성과 지표)
- MAU 증가
- POS 락인 (다른 서비스로 못 갈아타게)
- 부가서비스 판매 (구독/수수료 등 신규 매출)
- 이탈 감소

### 학습 관점
- 박오너는 화면을 매일 들여다보는 사람이 아니라, **전략을 결정하는 사람**이다. org 화면의 실제 사용자는 박세일즈(3B)이고, 박오너는 그 화면이 만들어내는 **숫자(MAU, 이탈률, 도입률)**로 판단한다.
- 즉 org 설계는 박세일즈의 일상 업무 흐름을 기준으로 하되, 박오너가 원하는 지표가 그 화면에서 자연스럽게 집계되어야 한다.

### 성공의 정의
"운영 OS를 붙이면 매장이 더 오래 남고, 더 많이 쓴다"는 증거를 데이터로 보여줄 수 있다.

### 제품에 주는 요구사항
- Demo Day 스토리라인이 박오너의 성과 지표(도입률, 활성도)로 요약될 수 있어야 한다
- TongssApp의 활동이 org에 도달해야 한다 → **05_DATA_CONTRACT의 존재 이유**

## 페르소나 3B — 박세일즈 (토스플레이스 가맹 운영 / CS / 영업 지원)

**한 줄:** 37만 매장을 챙겨야 하는데, 결제 데이터 말고는 매장을 모른다. org 화면을 실제로 매일 여는 사람.

### 프로필
- 토스플레이스 가맹 운영/CS/영업 지원 담당 `[확인필요: 실제 직무 명칭·조직 구조]`
- Salesforce 등 내부 관리 도구를 업무 시간 내내 사용한다

### 페인포인트
1. **결제 데이터는 보이지만, 이 매장이 잘 운영되고 있는지는 안 보인다.**
2. **도입 현황 파악이 수작업이다.** 어떤 매장이 어떤 기능을 쓰는지 흩어져 있다.
3. **추가 기능을 권하려 해도 매장별 맥락이 없다.**

### 원하는 것
- 어느 매장이 활발히 쓰고 어느 매장이 방치 중인지 한눈에 보고 싶다
- 문제가 생기기 전에 신호를 잡고 싶다
- 매장 단위로 히스토리를 보고 싶다

### 학습 관점
- 이 사용자는 **학습이 필요 없어야 한다.** 익숙한 Salesforce 문법(탭, 리스트뷰, 레코드 페이지) 안에 있어야 하고, 커스텀 UI는 최소로. → SLDS 준수, Base 컴포넌트 우선 원칙의 근거.
- TongssOrg의 실제 화면 설계 기준은 **박세일즈의 하루**다 (박오너는 그 위에서 지표만 본다).

### 성공의 정의
아침에 org를 열면 오늘 챙겨야 할 매장이 이미 정렬되어 있다.

### 제품에 주는 요구사항
- 매장(Account) 중심 데이터 모델
- 도입/활성 상태가 필드로 존재하고 리스트뷰로 필터 가능
- 매장별 히스토리(등록한 매뉴얼 수, 직원 학습 완료율 등)가 레코드 페이지에서 한눈에 보여야 한다

## 페르소나 간 관계 — 하나의 흐름

```
이대표(사장)가 매뉴얼을 등록한다
        ↓  [TongssApp]
김스태프(직원)가 현장에서 꺼내 보고, 익힌 것이 기록된다
        ↓  [데이터 계약]
박세일즈(토스, 실무)가 org에서 그 매장이 살아있음을 확인한다
        ↓  [집계]
박오너(토스, 의사결정자)가 그 숫자로 운영 OS 전략의 성과를 판단한다
```

네 페르소나는 각각의 사용자가 아니라 **하나의 가치 사슬**이다.
이 사슬이 끊기면 제품 주장도 끊긴다. → Demo Day 한 줄 시나리오와 동일. (00_WHY §5)

토스 쪽을 박오너(전략 근거)와 박세일즈(화면 사용자)로 나눈 이유: 00_WHY의 "왜 토스플레이스가 이걸 원하는가"는 박오너의 동기로 설명되지만, TongssOrg 화면을 실제로 여는 사람은 박세일즈다. 전략의 근거와 화면 설계의 기준을 분리해야 org를 잘못 설계하지 않는다.

## 리뷰 세션 안건 (Week 1, 전원)

1. 네 페르소나의 이름·프로필을 팀이 실제로 그릴 수 있는가? 아니면 너무 추상적인가
2. `[확인필요]` 항목 중 조사로 채울 것 / 가정으로 남길 것 구분
3. **김스태프의 학습 경험** — 은영·혜준 주도로 깊게. "매뉴얼이 너무 길다"는 페인포인트를 어떻게 설계 원칙으로 못 박을지가 승부처
4. **박오너 vs 박세일즈 — org 화면은 누구 기준으로 설계할 것인가** 최종 확정 (현재 문서는 "박세일즈 기준 설계 + 박오너용 지표 집계"로 잠정 결론)
5. 잘라낼 페인포인트 고르기 (5.5주 안에 다 못 다룬다. 페르소나별 **Top 2~3**만 남긴다)
6. 확정된 페인포인트 → 02_PRD 기능 목록으로 직접 연결 (00_WHY 부록 B의 기능 후보 리스트 참고)
